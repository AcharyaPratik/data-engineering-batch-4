Concept 1 of 7

DDL — Data Definition Language

DDL statements define the shape of your data — tables, columns, and the rules that guard them. They don't touch rows. CREATE, ALTER, and DROP are the three you'll use constantly; constraints are what make a table trustworthy instead of just a bag of columns.

CREATE TABLE — defining structure

Every column gets a type. Constraints attached to a column are rules the database enforces on every future insert or update — not suggestions.

sqlconstraints on the rides table
CREATE TABLE rides (
    ride_id     INTEGER PRIMARY KEY,        -- unique, never NULL, one per row
    driver_name VARCHAR(100) NOT NULL,  -- every row must have a value
    fare_amount NUMERIC(10,2) NOT NULL
                CHECK (fare_amount >= 0),        -- rejects negative fares
    ride_status VARCHAR(50) NOT NULL
                DEFAULT 'pending'               -- used when no value is given
                CHECK (ride_status IN ('no_show', 'completed', 'cancelled'))
);
ConstraintWhat it guarantees
PRIMARY KEYEvery value in this column is unique and never NULL — identifies the row
NOT NULLThis column cannot be left empty on insert
CHECK (...)A condition that must be true for every row — e.g. no negative fares
DEFAULTThe value used automatically when none is provided

ALTER TABLE — changing structure later

Requirements change. ALTER TABLE lets you add columns or constraints to a table that already has data in it.

sqladding a new status without breaking old rows
-- "pending" needs to become a valid ride_status too
ALTER TABLE rides
    ADD CONSTRAINT chk_ride_status
    CHECK (ride_status IN ('no_show', 'completed', 'cancelled', 'pending'));

Before / After — a table with no guardrails

sqlproblem: negative fare gets inserted silently
CREATE TABLE rides (
    ride_id     INTEGER PRIMARY KEY,
    fare_amount NUMERIC(10,2)     -- no CHECK, no NOT NULL
);

INSERT INTO rides (ride_id, fare_amount) VALUES (5001, -100);
-- INSERT 0 1  — succeeds. A ride now has a -100 fare.
-- Every SUM(fare_amount) report from here on is silently wrong.
sqlsolution: the database refuses bad data at insert time
CREATE TABLE rides (
    ride_id     INTEGER PRIMARY KEY,
    fare_amount NUMERIC(10,2) NOT NULL CHECK (fare_amount >= 0)
);

INSERT INTO rides (ride_id, fare_amount) VALUES (5001, -100);
-- ERROR: new row for relation "rides" violates check constraint
-- "rides_fare_amount_check"
-- The bad row never makes it in. The error happens where the mistake did.
⚠️
Watch out: adding a constraint with ALTER TABLE to a table that already has violating rows will fail immediately. Constraints are checked against existing data too, not just future inserts.
Concept 2 of 7

DML — Data Manipulation Language

Once the table exists, DML is how you change what's in it: INSERT adds rows, UPDATE changes existing rows, DELETE removes them. All three respect the constraints from Concept 1 — and all three are permanent the moment they run, unless you're inside a transaction.

INSERT — adding a row

sqlone new ride
INSERT INTO rides
    (ride_id, driver_name, passenger_name, pickup_city, dropoff_city,
     fare_amount, ride_distance_km, ride_status, requested_at, completed_at,
     rating, payment_method)
VALUES
    (5000, 'Bikash Karki', 'Sabina Dahal', 'Birgunj', 'Kathmandu',
     17.96, 31.75, 'completed', '2024-10-27 12:16:55', '2024-10-27 13:26:13',
     4.6, 'esewa');

-- Running it again with the same ride_id:
-- ERROR: duplicate key value violates unique constraint "rides_pkey"
-- PRIMARY KEY does its job — ride_id must be unique.

UPDATE — changing existing rows

sqlcorrecting a payment method
UPDATE rides
SET payment_method = 'esewa'
WHERE ride_id = 5000;

-- UPDATE 1  — exactly one row changed, because WHERE matched exactly one

DELETE — removing rows

sqlremoving a test row
DELETE FROM rides WHERE ride_id = 5000;

-- DELETE 1

Before / After — the WHERE clause is not optional

The single most dangerous mistake in SQL is forgetting WHERE on an UPDATE or DELETE. Without it, the statement applies to every row in the table.

sqlproblem: updates the entire table
UPDATE rides
SET ride_status = 'cancelled';

-- UPDATE 48213
--
-- Every ride in the table — completed, no_show, everything — is now
-- "cancelled". There was no WHERE, so there was no scope. This is
-- almost never recoverable without a backup.
sqlsolution: preview with SELECT, then scope with WHERE
-- Step 1: run the WHERE as a SELECT first, check the row count looks right
SELECT * FROM rides WHERE ride_id = 5001;
-- 1 row — good, that's the one row I meant to change

-- Step 2: run the same WHERE on the UPDATE
UPDATE rides
SET ride_status = 'cancelled'
WHERE ride_id = 5001;

-- UPDATE 1 — matches what you previewed, nothing more
🔴
Habit to build now: before any UPDATE or DELETE, run the same WHERE clause as a SELECT * first. If the row count matches what you expect, swap SELECT * for the real statement.
Concept 3 of 7

DQL — Data Query Language

DQL is just SELECT — but nearly everything you'll do with SQL this course is a variation on it. Choosing columns, filtering rows, ordering results, and limiting how many come back are the four building blocks every other concept in this pre-read sits on top of.

Choosing columns

sqlselect specific columns, not everything
SELECT ride_id, driver_name, passenger_name
FROM rides;

-- vs SELECT * — fine for exploring, but pulls every column
-- including ones you don't need. Name the columns you actually use.

Filtering with WHERE

sqlcomparison and logical operators
SELECT * FROM rides
WHERE ride_status = 'cancelled'
  AND payment_method = 'esewa';

-- Pattern matching with LIKE — % matches any sequence of characters
SELECT passenger_name FROM rides
WHERE driver_name LIKE '%Ramesh%';
OperatorMeaning
=, !=, <, >Standard comparisons
AND / ORCombine multiple conditions
IN (...)Matches any value in a list
LIKE '%text%'Pattern match — % is a wildcard for any characters
IS NULL / IS NOT NULLThe only correct way to test for missing values — see Concept 4

Ordering and limiting

sqltop 5 highest fares
SELECT driver_name, fare_amount
FROM rides
ORDER BY fare_amount DESC
LIMIT 5;

Before / After — case sensitivity in text comparisons

sqlproblem: "ramesh shrestha" ≠ "Ramesh Shrestha"
SELECT * FROM rides
WHERE driver_name = 'ramesh shrestha';

-- 0 rows.
-- The driver is stored as "Ramesh Shrestha". SQL string equality is
-- case-sensitive by default — this silently returns nothing instead
-- of an error, which is easy to miss.
sqlsolution: LOWER() both sides before comparing
SELECT LOWER('Ramesh Shrestha');
-- "ramesh shrestha"

SELECT * FROM rides
WHERE LOWER(driver_name) = LOWER('ramesh shrestha');

-- Matches regardless of how the name was typed on either side.
Concept 4 of 7

Working with NULL

NULL means unknown — not zero, not an empty string, not false. That single idea breaks a lot of intuition, because SQL's normal comparison operators weren't built to handle "unknown." This is the concept that causes the most silently wrong reports in this course, so read it slowly.

NULL breaks equality

sql= NULL is never true — not even for NULL itself
SELECT NULL = NULL;
-- NULL   (not TRUE — "unknown equals unknown" is still unknown)

SELECT * FROM rides WHERE rating = NULL;
-- 0 rows — always, no matter how many NULL ratings exist.
-- This query LOOKS correct and runs without error. It's just wrong.

SELECT * FROM rides WHERE rating IS NULL;
-- The correct way to test for a missing value.

NULL and COUNT()

sqlCOUNT(*) vs COUNT(column)
SELECT COUNT(*) FROM rides;
-- Total rows in the table — NULLs included, every row counts

SELECT COUNT(rating) FROM rides;
-- Only rows where rating IS NOT NULL — rides never rated are skipped

-- These two numbers being different is expected, not a bug —
-- it tells you how many rides have no rating at all.

Before / After — NULL disappearing from a filter

This exact bug shows up the moment you try to find "everything except X" — != silently drops every NULL row along with it.

sqlproblem: "not paid by cash" undercounts
SELECT COUNT(*) FROM rides
WHERE payment_method != 'cash';

-- Looks like: "every ride not paid in cash". It's actually:
-- "every ride with a KNOWN payment method that isn't cash."
-- Rides where payment_method is NULL (never recorded) vanish from
-- both this count AND a `= 'cash'` count. They're invisible either way.
sqlsolution: decide explicitly what to do with NULL
SELECT COUNT(*) FROM rides
WHERE payment_method != 'cash'
   OR payment_method IS NULL;

-- Now "not cash" correctly includes rides with an unrecorded method too.
-- Whether that's the RIGHT business rule is a separate question — but
-- now it's a decision you made on purpose, not one SQL made for you.
💡
COALESCE(column, default) returns the column's value, or a fallback if it's NULL — e.g. COALESCE(payment_method, 'unknown'). Handy for reports where you want missing values to show up instead of disappearing.
Concept 5 of 7

Aggregation & GROUP BY

An aggregate function takes many values and combines them into a single summary value — a count, a total, an average. GROUP BY is what lets you get one summary per category instead of one summary for the whole table — one row per driver instead of one row for everyone.

Aggregate functions on the whole table

sqlone summary row for all of rides
SELECT COUNT(*)              FROM rides;  -- how many rides total
SELECT SUM(fare_amount)      FROM rides;  -- total revenue
SELECT AVG(fare_amount)      FROM rides;  -- average fare
SELECT MIN(ride_distance_km) FROM rides;  -- shortest ride
SELECT MAX(ride_distance_km) FROM rides;  -- longest ride

GROUP BY — one row per category

sqlrides and revenue per driver
SELECT
    driver_name,
    COUNT(*)         AS total_rides,
    SUM(fare_amount) AS total_revenue
FROM rides
GROUP BY driver_name
ORDER BY total_revenue DESC;

-- One row PER DRIVER, not one row per ride. Rows with the same
-- driver_name get collapsed into a single summary row.

The one rule that trips everyone up

Every column in SELECT must either be inside an aggregate function, or listed in GROUP BY. SQL has no way to show one row per driver and a column with a different value on every underlying ride.

sqlproblem: which ride_id would this even show?
SELECT
    driver_name,
    ride_id,               -- ← not aggregated, not grouped
    COUNT(*)
FROM rides
GROUP BY driver_name;

-- ERROR: column "rides.ride_id" must appear in the GROUP BY clause
-- or be used in an aggregate function
--
-- Makes sense: a driver has many ride_ids. Which one should print?
sqlsolution: group by status too, or drop ride_id
SELECT
    driver_name,
    ride_status,            -- now listed in GROUP BY too
    COUNT(*)
FROM rides
GROUP BY driver_name, ride_status
ORDER BY driver_name;

-- One row per (driver_name, ride_status) combination — well-defined.
💡
Mental model: GROUP BY runs before SELECT. Picture it splitting the table into stacks of rows — one stack per unique combination of the grouped columns — then collapsing each stack into one output row.
Concept 6 of 7

HAVING

WHERE filters individual rows before grouping happens. HAVING filters the summary rows after grouping and aggregating. They look similar but run at different points in the query, which is exactly why one of them can reference COUNT(*) and the other can't.

The loyalty scheme query

Pathao wants drivers who completed more than 150 rides. "Completed" filters rows — that's WHERE. "More than 150" filters the count after grouping — that's HAVING.

sqldrivers who qualify for the bonus
SELECT
    driver_name,
    COUNT(*) AS completed_rides
FROM rides
WHERE ride_status = 'completed'     -- filters ROWS, before grouping
GROUP BY driver_name
HAVING COUNT(*) > 150            -- filters GROUPS, after aggregating
ORDER BY driver_name;

Why WHERE can't do this job

sqlproblem: COUNT(*) doesn't exist yet when WHERE runs
SELECT driver_name, COUNT(*)
FROM rides
WHERE ride_status = 'completed'
  AND COUNT(*) > 150              -- ← invalid here
GROUP BY driver_name;

-- ERROR: aggregate functions are not allowed in WHERE
--
-- WHERE filters rows one at a time, before GROUP BY has run.
-- There's no "count" yet for a single row to compare against.
sqlsolution: HAVING runs after COUNT(*) is known
SELECT driver_name, COUNT(*)
FROM rides
WHERE ride_status = 'completed'
GROUP BY driver_name
HAVING COUNT(*) > 150;

-- Works — by the time HAVING evaluates, every group already has
-- its final COUNT(*), so comparing against it is valid.

WHERE vs HAVING

WHEREHAVING
FiltersIndividual rowsGrouped/aggregated results
RunsBefore GROUP BYAfter GROUP BY
Can use aggregates?NoYes — that's the point
Works without GROUP BY?Yes — most common caseYes, treats whole table as one group

The real order SQL executes in

This is why WHERE can't see COUNT(*) and HAVING can — by the time each one runs, different things exist.

FROM→ WHERE→ GROUP BY→ HAVING→ SELECT→ ORDER BY→ LIMIT

Notice SELECT runs after WHERE, GROUP BY, and HAVING — which is also why you can't reference a column alias you defined in SELECT from inside a WHERE clause.

Concept 7 of 7

Putting it all together

Back to the loyalty scheme from page 0: Pathao wants every driver who has completed more than 150 rides, their total completed rides, and their average rating — but ratings are sometimes missing, and that has to be handled correctly, not ignored.

🎯
Before Class 2: read this query until you can explain what each clause does and, more importantly, the order they run in.
sqlloyalty_scheme_report.sql — the complete query
-- Drivers who completed more than 150 rides, with revenue and rating.
-- COUNT(rating) instead of COUNT(*) so unrated rides don't inflate
-- the denominator used for the average.

SELECT
    driver_name,
    COUNT(*)                          AS completed_rides,
    SUM(fare_amount)                  AS total_revenue,
    ROUND(AVG(fare_amount), 2)          AS avg_fare,
    COUNT(rating)                      AS rated_rides,
    ROUND(AVG(rating), 2)               AS avg_rating
FROM
    rides
WHERE
    ride_status = 'completed'              -- row filter: only completed rides count
GROUP BY
    driver_name                        -- one output row per driver
HAVING
    COUNT(*) > 150                       -- group filter: only qualifying drivers
ORDER BY
    total_revenue DESC
LIMIT
    20;

Where each concept lives in this query

  • DDL: this query only works because rides already enforces ride_status IN (...) and fare_amount >= 0 — garbage values can't sneak into the aggregates
  • DML: every row summed here originally arrived through an INSERT, and any correction to a fare or status happened through a scoped UPDATE
  • DQL: SELECT, FROM, ORDER BY, LIMIT — the query's basic shape
  • NULL: COUNT(rating) instead of COUNT(*) — unrated rides are excluded from avg_rating's denominator instead of silently dragging it toward zero
  • Aggregation & GROUP BY: COUNT, SUM, AVG per driver_name — one summary row per driver
  • HAVING: COUNT(*) > 150 — filters which driver groups make the final report, something WHERE is structurally unable to do
🎯
You're ready for Class 2 when you can read this query top to bottom and explain, clause by clause, what each one does and why it runs in that order. In class, you'll extend this pattern with joins across multiple tables.
