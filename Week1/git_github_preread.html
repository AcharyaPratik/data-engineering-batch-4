Concept 1 of 7

Git vs GitHub

These two names get used interchangeably but they are different things. Mixing them up is the fastest way to get lost in your first week, so it's worth being precise before you touch a single command.

Git — the tool on your laptop

Git is version control software that runs locally. It tracks every change you make to a folder of files over time, letting you save checkpoints (commits) and go back to any of them. Git works entirely offline — it doesn't need the internet or an account.

GitHub — the website that hosts your repo

GitHub is a website (and company) that hosts Git repositories in the cloud. It adds things Git itself doesn't have: a place to store your code online, a UI for browsing history, and collaboration features like forks and pull requests. GitLab and Bitbucket are competitors that do the same job — this course uses GitHub.

💡
One-line summary: Git is the engine, GitHub is where you park the car online and let other people look at it.

Vocabulary you'll use every day

TermWhat it means
repository (repo)A project folder tracked by Git — its full history of changes.
commitA saved snapshot of your changes, with a message describing what changed.
branchAn independent line of work — lets you build a feature without touching main.
remoteA version of the repo hosted elsewhere (e.g. on GitHub) that your local repo talks to.
cloneDownloading a full copy of a remote repo, with its whole history, onto your laptop.
forkA GitHub-only concept — your own personal copy of someone else's repo, under your account.
pull request (PR)A request to merge changes from one branch into another, opened for review.

The commands you already half-know

bashthe everyday loop
# Check what's changed since your last commit
git status

# Stage a file — mark it ready to be committed
git add day1_class_query.sql

# Save a snapshot with a message
git commit -m "Add day 1 class query"

# See the history of commits
git log --oneline
⚠️
Watch out: git commit only saves to your local repo. Nothing is visible on GitHub — or to your instructor — until you git push. Concept 5 covers this.
Concept 2 of 7

Forking the repo

You do not have write access to the course repository — and you shouldn't. Instead, every student forks it: GitHub creates a full copy under your own account that you fully own and can push to freely, while staying linked to the original so you can pull in new material later.

How to fork

  • Open the course repository on GitHub: github.com/bishalrijal/data-engineering-batch-4
  • Click the Fork button in the top-right corner
  • Confirm your account as the owner and click Create fork
  • GitHub redirects you to your own copy: github.com/<your-username>/data-engineering-batch-4
💡
Do this once per course, not once per assignment. Your fork sticks around for the whole term — you'll keep syncing new material into it week after week, covered in Concept 6.

Before / After — why you can't just clone the original

bashproblem: you don't own this repo
git clone https://github.com/bishalrijal/data-engineering-batch-4.git
cd data-engineering-batch-4
# ... you do your assignment, then:
git push origin main

# remote: Permission to bishalrijal/data-engineering-batch-4.git denied
# fatal: unable to access — 403
#
# You cloned the ORIGINAL repo. You have read access, not write access.
# There is nowhere for your commits to go.
bashsolution: fork on GitHub, then clone YOUR fork
# After clicking "Fork" on github.com/bishalrijal/data-engineering-batch-4
git clone https://github.com/YOUR-USERNAME/data-engineering-batch-4.git
cd data-engineering-batch-4
# ... you do your assignment, then:
git push origin main
# Works — this is your own repo, you have full write access.
🔴
The #1 week-one mistake: cloning bishalrijal/data-engineering-batch-4 directly instead of your own fork. If your terminal ever shows bishalrijal instead of your own username in a clone URL, stop and re-check.
Concept 3 of 7

Clone & remotes

Forking creates your copy on GitHub, but you need it on your own machine to actually write code. Cloning downloads it — and sets up a remote pointing back to it. You'll then add a second remote pointing to the original course repo, so you can pull in new lessons all term.

Clone your fork

bashdownloads your fork onto your laptop
git clone https://github.com/YOUR-USERNAME/data-engineering-batch-4.git
cd data-engineering-batch-4

# Git automatically named the remote for YOUR fork "origin"
git remote -v
# origin  https://github.com/YOUR-USERNAME/data-engineering-batch-4.git (fetch)
# origin  https://github.com/YOUR-USERNAME/data-engineering-batch-4.git (push)

Add the original repo as "upstream"

Right now your local repo only knows about your fork. It has no way to hear about new material added to the original course repo. Adding a second remote — conventionally named upstream — fixes that.

bashpoint to the instructor's original repo
git remote add upstream https://github.com/bishalrijal/data-engineering-batch-4.git

# Verify — you should now see two remotes
git remote -v
# origin    https://github.com/YOUR-USERNAME/data-engineering-batch-4.git (fetch)
# origin    https://github.com/YOUR-USERNAME/data-engineering-batch-4.git (push)
# upstream  https://github.com/bishalrijal/data-engineering-batch-4.git (fetch)
# upstream  https://github.com/bishalrijal/data-engineering-batch-4.git (push)

Concept 4 of 7

Branch & commit

Every assignment starts the same way: a fresh branch off main. This keeps your main branch clean — which matters, because main is exactly what you'll sync against the instructor's repo after every class. Work sitting directly on main makes that sync messy.

Create a branch for the assignment

bashone branch per assignment
# Make sure you're starting from an up-to-date main
git checkout main

# Create and switch to a new branch — name it after the assignment
git checkout -b week1-assignment

# Confirm which branch you're on
git branch
#   main
# * week1-assignment

Commit your work

bashstage and save your changes
# See what changed
git status

# Stage the files for this assignment
git add Week1/my_solution.sql

# Commit with a message describing what you did — not "update"
git commit -m "Add week 1 SQL solution: top drivers by fare"

# Repeat add/commit as you make progress — small, meaningful commits

Before / After — working on main vs a branch

bashproblem: main now diverges from upstream
git checkout main
# ... edit files, commit directly here ...
git commit -m "assignment"

# Next class, you try to sync new material:
git merge upstream/main
# CONFLICT (content): Merge conflict in Week1/notes.md
#
# Your assignment commits and the instructor's new files are now tangled
# together on the same branch. Every future sync repeats this pain.
bashsolution: main stays clean, assignments live on branches
git checkout -b week1-assignment
# ... edit files, commit here instead ...
git commit -m "Add week 1 SQL solution"

# main never received any assignment commits — it's identical to
# upstream/main. Syncing next class is a clean fast-forward, no conflicts.
💡
Rule of thumb: the only thing that ever touches your main branch is a sync from upstream. Every assignment gets its own branch, named after the assignment.
Concept 5 of 7

Push & open a pull request

Commits made so far only exist on your laptop. git push uploads your branch to your fork on GitHub. From there, you open a pull request — but the base and head both stay inside your own fork. You are not sending anything to the instructor's repository.

Push your branch to your fork

bashuploads to origin — your fork
# Push the branch, and tell git to remember this upstream tracking link
git push -u origin week1-assignment

# remote: Create a pull request for 'week1-assignment' on GitHub by visiting:
# remote:   https://github.com/YOUR-USERNAME/data-engineering-batch-4/pull/new/week1-assignment

Open the PR — on your own fork

  • Go to your fork on GitHub: github.com/YOUR-USERNAME/data-engineering-batch-4
  • Click Compare & pull request for your branch
  • Check the base repository dropdown — it must read YOUR-USERNAME/data-engineering-batch-4, base: main
  • Head repository is YOUR-USERNAME/data-engineering-batch-4, compare: week1-assignment
  • Add a short title and description, then click Create pull request
  • Share the PR link with your instructor for review
🔴
The mistake that trips people up here: GitHub sometimes defaults the base repository to bishalrijal/data-engineering-batch-4 instead of your own fork, because that's where you forked from. Always check the base dropdown before clicking create — your assignment PR should merge into your main, not the instructor's.

Before / After — PR target

textproblem: base repo left on the default
base repository:  bishalrijal/data-engineering-batch-4   base: main

# This PR now asks to merge your assignment into the INSTRUCTOR'S repo.
# The instructor doesn't want 30 students merging directly into course
# material, and you don't have permission to merge it anyway — it just
# sits open and confuses everyone.
textsolution: base repo switched to your own fork

💡
Why bother with a PR to yourself? It gives your instructor a clean diff to review and comment on, exactly like a real-world code review — without needing write access to your fork or you needing write access to the course repo.
Concept 6 of 7

Sync with upstream

After every class, new material — code, datasets, notes — gets pushed to the original course repository. Your fork does not update itself. You need to explicitly pull those changes in, ideally right before you start the next assignment.

The command-line way

bashrun this after every class
# 1. Switch to your local main branch
git checkout main

# 2. Download the latest history from the instructor's repo
git fetch upstream

# 3. Merge it into your local main
git merge upstream/main

# 4. Push the update back up to your fork on GitHub
git push origin main

Steps 2 and 3 can be combined into one command:

bashshortcut: fetch + merge in one step
git checkout main
git pull upstream main
git push origin main

The no-terminal way: GitHub's Sync fork button

If you'd rather not use the command line for this, GitHub can do steps 2–4 for you in the browser:

  • Open your fork: github.com/YOUR-USERNAME/data-engineering-batch-4
  • Click Sync fork near the top of the file list
  • Click Update branch
  • Back on your laptop, run git pull origin main to bring the update down locally

Before / After — forgetting to sync

bashproblem: missing files, and a messy merge later
# Week 3 starts. You never synced after Week 2.
git checkout -b week3-assignment
cd Week3
# bash: cd: Week3: No such file or directory
#
# Week 3 material doesn't exist in your fork yet. You'd need to sync now
# anyway — except your assignment branch already has commits on it,
# making the sync more complicated than it needed to be.
bashsolution: sync main, then branch off the fresh copy
git checkout main
git pull upstream main
git push origin main

# Now Week3/ exists locally. Branch off the up-to-date main:
git checkout -b week3-assignment
💡
Habit to build: sync main before creating each new assignment branch, not after. Concept 4's rule — never commit directly on main — is exactly what makes this sync painless every time.

Putting it all together

Two setup steps happen once. Then you repeat the same short loop for every assignment, all course long. Bookmark this page.

🎯
Before Week 1 class: complete the one-time setup below so you're not doing it live during class time.
bashone-time setup — do this before Week 1
# 1. Fork on GitHub (in your browser)
#    github.com/bishalrijal/data-engineering-batch-4 → click "Fork"

# 2. Clone YOUR fork
git clone https://github.com/YOUR-USERNAME/data-engineering-batch-4.git
cd data-engineering-batch-4

# 3. Add the instructor's repo as "upstream"
git remote add upstream https://github.com/bishalrijal/data-engineering-batch-4.git

# 4. Confirm both remotes are set
git remote -v
bashper-assignment loop — repeat every week
# 1. Sync main with the instructor's latest material
git checkout main
git pull upstream main
git push origin main

# 2. Create a branch for this week's assignment
git checkout -b week2-assignment

# 3. Do the work, commit as you go
git add Week2/solution.sql
git commit -m "Add week 2 solution"

# 4. Push the branch to your fork
git push -u origin week2-assignment

# 5. Open a pull request on GitHub
#    base repo: YOUR-USERNAME/data-engineering-batch-4   base: main
#    head repo: YOUR-USERNAME/data-engineering-batch-4   compare: week2-assignment
#    → Create pull request → share the link with your instructor

Where each concept lives in this loop

  • Fork: a one-time click on GitHub that gives you your own copy of the course repo
  • Clone & remotes: origin is your fork (push here), upstream is the instructor's repo (pull from here)
  • Branch: git checkout -b week2-assignment — one per assignment, off a freshly synced main
  • Commit: git add + git commit -m "..." — small, meaningful snapshots as you work
  • Push & PR: git push -u origin <branch>, then open a PR with both base and head on your own fork
  • Sync: git pull upstream main then git push origin main — run this after every class, before branching
🎯
You're ready for Week 1 when your fork is cloned, both remotes are configured, and you can describe — without looking back — why assignment PRs target your own fork instead of the instructor's repo.
