Concept 1 of 7

Case & whitespace

CSV data is typed by different people, at different times, in different moods. The same driver ends up as "Ramesh Shrestha", "ramesh shrestha", and " Ramesh Shrestha " across different rows. Fixing case and whitespace is the very first thing you do to any text column — before comparing it, grouping it, or inserting it anywhere.

LOWER, UPPER, INITCAP

sqlnormalizing case
SELECT LOWER('Ramesh Shrestha');
-- ramesh shrestha

SELECT UPPER('completed');
-- COMPLETED

SELECT INITCAP('ramesh shrestha');
-- Ramesh Shrestha  (title case — capitalizes each word)

-- Normalize before comparing
WHERE LOWER(driver_name) = LOWER('ramesh shrestha')

LOWER is the workhorse — use it any time you're comparing or grouping text. UPPER is mainly for canonical codes and labels. INITCAP is for display: turning a lowercased value back into something presentable.

TRIM, LTRIM, RTRIM

sqlremoving stray whitespace
SELECT TRIM('  Kathmandu  ');
-- Kathmandu   (strips both sides — what you want 95% of the time)

SELECT LTRIM('   hello');   -- 'hello'  (left side only)
SELECT RTRIM('hello   ');   -- 'hello'  (right side only)

-- TRIM can also strip specific characters, not just spaces
SELECT TRIM(BOTH ',' FROM ',hello,');
-- hello

-- LOWER + TRIM together — the standard cleaning pair
LOWER(TRIM(driver_name))

Before / After — a driver split into two rows

sqlproblem: one driver, two rows
SELECT driver_name, COUNT(*)
FROM rides_staging
GROUP BY driver_name;

-- driver_name          | count
-- Ramesh Shrestha      | 812
-- ramesh shrestha      | 41
--
-- Same human, split into two rows because GROUP BY treats
-- "Ramesh Shrestha" and "ramesh shrestha" as different values.
sqlsolution: normalize before grouping
SELECT LOWER(TRIM(driver_name)) AS driver_name, COUNT(*)
FROM rides_staging
GROUP BY LOWER(TRIM(driver_name));

-- driver_name          | count
-- ramesh shrestha      | 853
--
-- One row, correct total. This is exactly why the migration script
-- normalizes names before ever inserting them into the drivers table.
Concept 2 of 7

Replace, combine & NULLs

Once case and whitespace are handled, you'll still hit specific typos, need to join columns together, and — almost always — need to decide what happens when a value is simply missing. REPLACE, CONCAT, COALESCE, and NULLIF cover all three.

REPLACE — exact substring swap

sqlfixing known values
-- Fix a known typo in city names
REPLACE(city_name, 'Kathamndu', 'Kathmandu')

-- Remove dashes from phone numbers
REPLACE(phone, '-', '')
-- '98-4100-1234'  →  '9841001234'

-- Replace spaces with underscores
REPLACE('New Road', ' ', '_')
-- New_Road

REPLACE is case-sensitive and only matches the exact substring you give it. When you need to match a pattern instead of a literal string — "any digit," "anything that isn't a letter" — you need REGEXP_REPLACE, covered in Concept 5.

CONCAT and the || operator

sqljoining strings
-- Build a full name from parts
CONCAT(first_name, ' ', last_name)

-- Same thing with the || operator
first_name || ' ' || last_name

-- Build a readable label
CONCAT(city_name, ' (', country, ')')
-- Kathmandu (NP)
💡
The one difference that matters: CONCAT skips NULLs silently. || returns NULL for the whole expression if any single part is NULL — 'Ramesh' || NULL || 'Shrestha' is just NULL, not 'RameshShrestha'.

LENGTH — measuring strings

sqlvalidating before insert
SELECT LENGTH('Kathmandu');
-- 9

-- Find suspiciously short names — likely bad data
SELECT driver_name FROM rides_staging
WHERE LENGTH(TRIM(driver_name)) < 3;

COALESCE and NULLIF — handling missing values

sqldefaults for NULL
-- COALESCE returns the first non-NULL argument
COALESCE(payment_method, 'unknown')

-- NULLIF returns NULL if the two arguments are equal, else the value
NULLIF(TRIM(payment_method), '')
-- '   '  →  NULL   (turns a blank string into a real NULL)

-- Combined: the standard "fill in the blank" pattern
COALESCE(NULLIF(TRIM(payment_method), ''), 'unknown')

Before / After — TRIM doesn't make blanks into NULL

sqlproblem: '' is not NULL
COALESCE(payment_method, 'unknown')

-- payment_method = '   '  (blank, but not NULL — someone left the field
-- empty in the source CSV)
--
-- Result: '   '  — COALESCE only replaces actual NULLs. An empty or
-- whitespace-only string sails right through untouched.
sqlsolution: NULLIF first, then COALESCE
COALESCE(NULLIF(TRIM(payment_method), ''), 'unknown')

-- TRIM('   ')            → ''     (still not NULL)
-- NULLIF('', '')         → NULL   (now it is)
-- COALESCE(NULL, 'unknown') → 'unknown'
--
-- Result: 'unknown' — blank values are caught and defaulted correctly.
⚠️
Remember this one: TRIM(' ') returns '' (empty string), not NULL. If you want blank-only values treated as missing, you always need NULLIF before COALESCE — never assume TRIM alone gets you there.
Concept 3 of 7

Search & pattern matching

Sometimes you don't need to clean a value — you need to find rows matching a partial pattern. LIKE, ILIKE, and POSITION let you filter and search text without an exact match.

LIKE and ILIKE

sqlwildcard matching
-- LIKE: case-sensitive
SELECT * FROM rides WHERE driver_name LIKE 'Ramesh%';
-- Matches 'Ramesh Shrestha', 'Ramesh K.' — NOT 'ramesh shrestha'

-- ILIKE: case-insensitive (PostgreSQL extension)
SELECT * FROM rides WHERE driver_name ILIKE 'ramesh%';
-- Matches 'Ramesh', 'RAMESH', 'ramesh' — all of them

-- Wildcard on both sides = "contains"
WHERE city_name ILIKE '%mandu%'
WildcardMatches
%Zero or more of any character
_Exactly one of any character — LIKE 'R_mesh' matches "Ramesh" but not "Raamesh"

POSITION and STRPOS

sqlfinding where a substring sits
-- POSITION syntax — strings are 1-indexed in PostgreSQL
POSITION('@' IN 'user@example.com');
-- 5

-- STRPOS — same result, different argument order
STRPOS('user@example.com', '@');
-- 5   (returns 0 if the substring isn't found — never NULL)

-- Find rows where city has a space (compound city names)
WHERE STRPOS(city_name, ' ') > 0

STARTS_WITH and ENDS_WITH

sqlprefix / suffix checks
STARTS_WITH('Kathmandu', 'Kath');   -- true
ENDS_WITH('completed', 'ed');      -- true

-- Cleaner than LIKE for a simple prefix check
WHERE STARTS_WITH(status, 'comp')

STARTS_WITH is case-sensitive — for a case-insensitive prefix check, use ILIKE 'prefix%' instead.

Before / After — a case-sensitive filter drops real rows

sqlproblem: undercounts esewa payments
SELECT COUNT(*) FROM rides_staging
WHERE payment_method LIKE 'esewa';

-- payment_method was typed by hand during signup — the raw data has
-- 'esewa', 'Esewa', and 'ESEWA' all meaning the same payment method.
-- LIKE 'esewa' only matches the exact lowercase spelling, silently
-- undercounting the true total.
sqlsolution: ILIKE ignores case entirely
SELECT COUNT(*) FROM rides_staging
WHERE payment_method ILIKE 'esewa';

-- Matches 'esewa', 'Esewa', 'ESEWA' — every casing variant recorded,
-- correct total. (In the migration script itself, you'd still run
-- LOWER(TRIM(payment_method)) once at insert time so this problem
-- never comes back.)
Concept 4 of 7

Extract & split

Some columns pack more than one piece of information into a single string — an email with a domain, a "City, Province" pair, a file path. These functions pull specific pieces back out.

SUBSTRING, LEFT, RIGHT

sqlgrabbing part of a string by position
-- SUBSTRING: from position, for a length (1-indexed)
SUBSTRING('Kathmandu' FROM 1 FOR 4);
-- Kath

-- Extract a year from a date string
SUBSTRING('2024-03-15' FROM 1 FOR 4);
-- 2024

-- LEFT / RIGHT: simpler when you just need the start or end
LEFT('Kathmandu', 4);    -- Kath
RIGHT('Kathmandu', 4);   -- andu
RIGHT('Kathmandu NP', 2);  -- NP  (country code from the end)

SPLIT_PART — parsing delimited text

sqlsplitting on a delimiter
-- Split an email into username and domain
SPLIT_PART('ramesh@example.com', '@', 1);   -- ramesh
SPLIT_PART('ramesh@example.com', '@', 2);   -- example.com

-- Extract the city from "City, Province"
SPLIT_PART('Kathmandu, Bagmati', ',', 1);
-- Kathmandu

-- Last segment of a path
SPLIT_PART('/data/2024/rides.csv', '/', 4);
-- rides.csv
💡
SPLIT_PART returns an empty string, not NULL, if the requested part doesn't exist. And parts are numbered starting at 1, not 0.

LPAD and RPAD — padding for fixed width

sqlformatting IDs and columns
-- Zero-pad a numeric ID to 6 digits
LPAD(CAST(driver_id AS TEXT), 6, '0');
-- 42  →  '000042'

-- Right-pad to align column output
RPAD(city_name, 15, ' ');
-- 'Dharan         '

Concept 5 of 7

REGEXP_REPLACE

REPLACE only matches an exact substring you already know. Sometimes you need to describe a pattern instead — "remove any digit," "strip everything that isn't a letter." That's what a regular expression (regex) does, and REGEXP_REPLACE is how PostgreSQL applies one.

What is a regular expression?

A regex is a pattern that describes a set of strings, not one specific string. These are the building blocks you'll actually use for cleaning:

PatternWhat it matchesExample match
[0-9]Any single digit'9' in 'NP9841'
[^0-9]Any character that is not a digit'N', 'P' in 'NP9841'
[a-zA-Z]Any letter'R' in 'Ramesh'
\sAny whitespace (space, tab, newline)the space in 'New Road'
\s+One or more whitespace characters' ' (multiple spaces)
[^a-zA-Z\s]Anything that isn't a letter or spacedigits, dashes, brackets
^Start of string — anchors the pattern to the beginning—
$End of string — anchors the pattern to the end—

REGEXP_REPLACE syntax

sqlREGEXP_REPLACE( string, pattern, replacement, flags )
-- Remove ALL digits — flag 'g' means "replace every match, not just the first"
REGEXP_REPLACE('Ramesh123', '[0-9]', '', 'g');
-- Ramesh

-- Keep only digits (remove everything that ISN'T a digit)
REGEXP_REPLACE('98-4100 1234', '[^0-9]', '', 'g');
-- 9841001234

-- Collapse multiple spaces into one
REGEXP_REPLACE('New   Road', '\s+', ' ', 'g');
-- New Road

-- Remove special characters, keep letters and spaces
REGEXP_REPLACE(city_name, '[^a-zA-Z\s]', '', 'g')

-- Flag 'i' = case-insensitive: strip a trailing 'np' or 'NP'
REGEXP_REPLACE('Kathmandu NP', 'np$', '', 'gi');
-- 'Kathmandu '

Concept 6 of 7

Migration patterns

These are the actual patterns you'll write in the Week 2 migration script. Each one chains together functions from the concepts above to solve one specific problem in rides.csv.

1
Normalize names before inserting or matching
Always apply LOWER + TRIM together — then INITCAP if you want a clean display form — before inserting into a lookup table, and before matching against it later.
sqldrivers lookup table
-- Insert distinct driver names, cleaned
INSERT INTO drivers (name)
SELECT DISTINCT
    INITCAP(LOWER(TRIM(driver_name)))
FROM rides_staging
WHERE TRIM(driver_name) != ''
  AND driver_name IS NOT NULL;

-- Later: match using the exact same normalization
SELECT driver_id FROM drivers
WHERE name = INITCAP(LOWER(TRIM(rs.driver_name)))
2
Clean city names — strip symbols, collapse spaces
City data from CSVs often carries extra punctuation, trailing commas, or double spaces. Chain TRIM + REGEXP_REPLACE to produce one canonical form.
sqllocations lookup table
-- Remove anything that isn't a letter, digit, or space,
-- then collapse multiple spaces, then trim the edges
TRIM(
  REGEXP_REPLACE(
    REGEXP_REPLACE(city_name, '[^a-zA-Z0-9\s]', '', 'g'),
    '\s+', ' ', 'g'
  )
)

-- Example transformations:
-- '  Kath,mandu!!'  →  'Kathmandu'
-- 'New  Road  '     →  'New Road'
-- 'Dharan, '        →  'Dharan'
3
Normalize status values
The status column may hold 'Completed', 'COMPLETED', and 'completed' — all meaning the same thing. Standardize to lowercase before inserting, then lock it in with a CHECK constraint.
sqlstatus column
LOWER(TRIM(status)) AS status

-- Input variations → output
-- 'Completed '  →  'completed'
-- 'CANCELLED'   →  'cancelled'
-- ' pending'    →  'pending'

-- Add a CHECK constraint so future data stays clean
status TEXT CHECK(status IN ('completed', 'cancelled', 'pending'))
4
Handle NULLs and empty strings safely
The NULLIF-then-COALESCE pattern from Concept 2 — this is where it actually gets used, once per nullable column in the migration.
sqlpayment_method column
COALESCE(NULLIF(TRIM(payment_method), ''), 'unknown')
-- ''     →  'unknown'
-- NULL   →  'unknown'
-- 'cash' →  'cash'
5
The full migration SELECT — all cleaning combined
This is what INSERT INTO trips … SELECT looks like once every column has been cleaned. Each foreign key is resolved by matching the cleaned text against the lookup tables built in steps 1–2.
sqlrides_to_trips_migration.sql
INSERT INTO trips
    (driver_id, rider_id, pickup_location_id, dropoff_location_id,
     fare_amount, distance_km, status, payment_method, rating)
SELECT
    -- Resolve FK: look up driver_id using cleaned name
    (SELECT d.driver_id FROM drivers d
     WHERE  d.name = INITCAP(LOWER(TRIM(rs.driver_name))))  AS driver_id,

    (SELECT r.rider_id FROM riders r
     WHERE  r.name = INITCAP(LOWER(TRIM(rs.rider_name))))   AS rider_id,

    (SELECT l.location_id FROM locations l
     WHERE  l.city_name = TRIM(rs.pickup_city))              AS pickup_location_id,

    (SELECT l.location_id FROM locations l
     WHERE  l.city_name = TRIM(rs.dropoff_city))             AS dropoff_location_id,

    rs.fare_amount,
    rs.distance_km,
    LOWER(TRIM(rs.status))                                  AS status,
    COALESCE(NULLIF(TRIM(rs.payment_method), ''), 'unknown') AS payment_method,
    rs.rating
FROM rides_staging rs;
